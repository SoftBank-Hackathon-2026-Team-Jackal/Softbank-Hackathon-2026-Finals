# CDC PoC 2단계: AWS ↔ GCP

1단계 PoC(`../`)를 실제 클라우드 두 곳에 올려서, 클라우드 사이에서도 무중단 전환과 롤백이 되는지 검증합니다. 스크립트는 1단계와 같은 것을 그대로 씁니다.

## 구성

```
AWS prod 계정 (ap-northeast-2)                         GCP sbh26-prod (asia-northeast3)
┌──────────────────────────────────────┐            ┌──────────────────────────────┐
│ EC2 t3.small  env-a                  │  WireGuard │ GCE e2-small  env-b          │
│  loadgen → PgBouncer → pg-a          │◀══════════▶│  pg-b                        │
│  toolbox (scripts/)                  │ UDP 51820  │                              │
│  wg0 10.100.0.1                      │  RTT ~3ms  │  wg0 10.100.0.2              │
└──────────────────────────────────────┘            └──────────────────────────────┘
```

| 항목 | 내용 |
|---|---|
| 열린 포트 | 양쪽 모두 **WireGuard(UDP 51820)만**, 그것도 상대 VM의 고정 IP에서 오는 것만 허용합니다. SSH는 열지 않습니다 |
| DB 포트 | pg-a와 pg-b의 5432는 WireGuard 주소에만 바인딩합니다 |
| env-a 접속 | SSM `send-command` (`run.sh`). 로컬에 session-manager-plugin이 없어도 됩니다 |
| env-b 확인 | `gcloud compute instances get-serial-port-output` (시작 스크립트 로그) |
| PoC 파일 전달 | Terraform이 `../`를 zip으로 묶어 S3에 올리고, env-a가 받아 갑니다 |
| 이름 | pg-b가 원격에 있어도 이름은 그대로 `pg-b`입니다. `../compose.cloud-a.yml`이 `/etc/hosts`로 10.100.0.2를 가리키게 하므로 스크립트를 고치지 않습니다 |

## 실행

```bash
aws sso login --sso-session sbh26
export GOOGLE_OAUTH_ACCESS_TOKEN=$(gcloud auth print-access-token --account=alus20x@gmail.com)

terraform init
terraform apply                       # VM 2대 생성. 시작 스크립트가 끝날 때까지 약 3분

./run.sh 'wg show; ping -c3 10.100.0.2'         # 터널 확인
./run.sh 'scenarios/01_round_trip.sh'           # 왕복 시나리오

# PoC 파일을 고친 뒤
terraform apply && ./run.sh sync

terraform destroy                     # 다 쓰면 지운다
```

`run.sh`는 env-a의 `/opt/cdc`에서 `REMOTE_NODES=pg-b`를 설정하고 명령을 실행합니다. 시나리오는 시작할 때 env-a를 `docker compose down -v`로 지우고, 원격 pg-b는 `scripts/reset_node.sh`로 초기화합니다.

## 5GB 시나리오 (`scenarios/04_realistic.sh`, 2026-11-03)

쇼핑몰 스키마 7개 테이블, 약 4,100만 행(4.4GB)을 기존 데이터로 두고, 초당 200 트랜잭션을 섞어서 넣으면서 이전했습니다(주문 60%, 상태 변경 25%, 조회 10%, 취소 4%, 로그 정리 1%). 초기 복사 도중에는 상품 10만 건의 가격을 한 트랜잭션으로 바꾸는 배치를 실행했습니다. VM은 t3.large와 e2-standard-2입니다.

| 항목 | 결과 |
|---|---|
| DB 크기 | 4,423MB |
| WireGuard 대역폭 (iperf3) | 1,248Mbps (약 156MB/s) |
| 초기 복사 | 335초, **13.2MB/s** |
| 복사 중 원본 슬롯이 붙잡은 WAL | 최대 500MB |
| 복사 직후 따라잡기 | 약 48MB 지연을 5초 안에 해소 |
| 실시간 동기화 중 최대 지연 | 229KB |
| 쓰기 중단 (PAUSE 명령부터 RESUME까지) | 전환 1,304ms, 롤백 1,505ms |
| 부하 생성기 | 9만 7,670건 성공, **에러 0**, p50 10.7ms, p99 89.9ms |
| 유실 | pg-a 0, pg-b 0 |
| 전체 체크섬 (부하 중지 후) | 일치, 115초 |

전환 한 번의 단계별 시간(ms)은 다음과 같습니다. PAUSE 안에서는 데이터가 커서 체크섬 대신 테이블별 `max(id)`를 비교합니다(`VERIFY_IN_PAUSE=light`).

| 진행 중 트랜잭션 대기 | marker 도착 | 검증 | 정방향 삭제 + 시퀀스 + 역방향 켜기 | 대상 변경 + RESUME |
|---|---|---|---|---|
| 182 | 280 | 262 | 373 | 207 |

부하 생성기의 최대 지연 3.2초는 전환 때가 아니라 배치 작업 때 나왔습니다. 배치가 상품 행 10만 건을 3.1초 동안 잠갔기 때문입니다. 전환할 때의 최대 지연은 1.4초와 1.6초였습니다.

### 규모를 키우자 드러난 문제

처음 실행에서는 다음 문제가 나왔고, 모두 고친 뒤 위 결과를 얻었습니다.

| 문제 | 원인 | 조치 |
|---|---|---|
| 시드 생성 실패 | `g * 7919`가 `integer` 범위를 넘음 | `bigint`로 계산 |
| 시드 생성 실패 | Docker 기본 `/dev/shm` 64MB로는 병렬 쿼리 공유 메모리가 부족 | `shm_size: 1gb` |
| 처리량이 목표의 5% (초당 10건) | 고객별 최근 주문 조회가 PK 역순 스캔으로 500만 행을 읽음 | `(customer_id, id DESC)` 인덱스 |
| 쓰기 중단을 855ms로 잘못 측정 (실제 약 9초) | PAUSE가 진행 중인 트랜잭션을 기다리는 시간을 빼고 측정 | PAUSE 명령부터 측정, `PAUSE_TIMEOUT_SEC`(기본 5초)를 넘으면 전환 중단 |
| 배치가 교착 상태로 롤백 | 배치와 앱이 상품 행을 서로 다른 순서로 잠금 | 배치도 id 순서로 잠금 |

### 해석

- **초기 복사를 늦춘 것은 네트워크가 아닙니다.** 대역폭은 156MB/s였지만 복사는 13.2MB/s였습니다. 대상 DB가 행을 넣으면서 인덱스도 갱신하는 것이 병목입니다. 회선을 키워도 복사 시간은 거의 줄지 않습니다. 빠르게 하려면 PostgreSQL 17 `pg_createsubscriber`(물리 복제로 블록을 복사한 뒤 논리 구독으로 전환)나, 인덱스를 나중에 만드는 방식을 써야 합니다.
- **복사가 길어질수록 원본 디스크 부담이 커집니다.** 초당 200 트랜잭션으로 5분 반 동안 복사하자 원본 슬롯이 WAL 500MB를 붙잡았습니다. 복사 시간과 쓰기량에 비례하므로, 큰 DB에서는 원본 디스크 여유를 사전 점검에 넣어야 합니다.
- **쓰기 중단의 대부분은 스크립트 오버헤드입니다.** 단계마다 psql을 새로 띄우면서 WireGuard 너머로 연결하고 인증을 다시 합니다. 다음 개선 후보는 아래와 같습니다.

## 더 줄일 수 있는 곳

- **동기 복제 창:** 전환 직전 몇 초 동안만 원본에 `synchronous_standby_names`를 설정해, 커밋마다 대상 반영을 확인합니다. PAUSE 순간 대상이 이미 최신이므로 marker 대기가 필요 없습니다.
- **PAUSE 밖으로 빼기:** 시퀀스는 PAUSE 전에 여유값을 두고 올려 두고, 검증은 전환 직후에 합니다.
- **연결 유지:** 한 세션을 유지하고, 대상 DB 연결은 PgBouncer에서 미리 열어 둡니다.
- 위 세 가지를 합치면 PAUSE 안에는 진행 중 트랜잭션 대기와 대상 변경만 남습니다. 예상 쓰기 중단은 50~100ms입니다.
- **시점 선택:** 긴 트랜잭션이나 배치가 없는 순간을 에이전트가 골라서 전환합니다.

## 주의

- WireGuard 개인 키가 Terraform state(S3, 암호화)와 VM user_data, metadata에 들어 있습니다. PoC 한정입니다.
- DB 비밀번호는 1단계와 같은 고정값이며, WireGuard 주소에서만 접근할 수 있습니다.
- 켜 두는 동안 비용이 나갑니다. 기본값(t3.large, e2-standard-2, 디스크 60GB)은 시간당 약 0.2달러(하루 약 5달러)입니다. 가벼운 시나리오만 돌릴 때는 `-var env_a_instance_type=t3.small -var env_b_machine_type=e2-small -var disk_gb=20`으로 줄입니다.
- **Terraform은 작업 폴더의 `poc/cdc`를 그대로 묶어서 올립니다.** 다른 브랜치를 체크아웃한 상태에서 apply하면 그 브랜치의 파일이 VM에 올라갑니다.
