CDC 설계: PostgreSQL 논리 복제

가동 중인 DB를 멈추지 않고 옮기기 위해, 기존 데이터는 한 번 복사하고 그 이후의 변경은 WAL을 읽어 새 DB에 순서대로 재생합니다. 별도 CDC 도구 없이 PostgreSQL 내장 기능으로 구현합니다.

02CDC의 원리

PostgreSQL은 데이터를 바꿀 때 테이블 파일보다 WAL(Write-Ahead Log)에 먼저 기록하고, 각 기록에 위치 번호 LSN을 붙입니다. CDC는 이 WAL을 읽어서 다른 DB에 똑같이 재생하는 것입니다. wal_level = logical로 설정해야 행 단위 변경을 복원할 정보가 WAL에 함께 기록됩니다.

구성 요소위치하는 일
복제 슬롯pg-aWAL 안의 책갈피입니다. 구독자가 받아 간 위치를 기억하고, 받아 가기 전까지 이후 WAL을 지우지 못하게 붙잡습니다.
논리 디코딩pg-aWAL을 INSERT orders(id=42, …) 같은 행 단위 변경으로 바꿉니다. 커밋된 트랜잭션만, 커밋 순서대로 내보냅니다.
publicationpg-a어떤 테이블의 변경을 내보낼지 정합니다.
subscriptionpg-bpg-a에 접속해 변경 스트림을 받습니다.
apply workerpg-b받은 변경을 적용하고, 반영한 위치를 pg-a에 알립니다. UPDATE와 DELETE는 PK로 대상 행을 찾고, PK가 없으면 REPLICA IDENTITY FULL이 필요합니다.

03시간 순서: 덤프에서 CDC까지

정상 상태에서 지연량은 다음처럼 측정하며, 대시보드의 CDC 지연 그래프가 이 값입니다.

지연량 = pg-a의 현재 WAL 위치 − 슬롯이 확인받은 위치

04덤프와 CDC를 잇는 두 가지 방법

방법 A · MVP 채택

스키마만 pg_dump로 옮기고, 데이터는 구독을 만들 때 초기 복사와 CDC가 자동으로 이어지게 합니다.

# 1. 스키마만 덤프 (DDL은 복제되지 않음)
pg_dump --schema-only "$PG_A" | psql "$PG_B"

-- 2. pg-a
CREATE PUBLICATION mig_pub FOR ALL TABLES;

-- 3. pg-b
CREATE SUBSCRIPTION mig_sub
  CONNECTION 'host=10.100.0.1 dbname=app
              user=replicator'
  PUBLICATION mig_pub
  WITH (copy_data = true);

방법 B · 대용량 경로

슬롯을 만들면서 스냅샷 이름을 받고, 그 스냅샷으로 데이터를 직접 덤프한 뒤 CDC만 시작합니다.

# 1. 복제 연결로 슬롯 + 스냅샷 생성
CREATE_REPLICATION_SLOT mig_slot
  LOGICAL pgoutput EXPORT_SNAPSHOT
# ※ 덤프가 끝날 때까지 연결 유지

# 2. 같은 스냅샷으로 병렬 덤프·복원
pg_dump --snapshot=<이름> -Fd -j 4 ...
pg_restore ...

-- 3. 만들어 둔 슬롯으로 CDC만 시작
CREATE SUBSCRIPTION mig_sub ...
  WITH (copy_data = false,
        create_slot = false,
        slot_name = 'mig_slot');
방법 A방법 B
구현 난이도낮음 (SQL 몇 줄)높음 (스냅샷 연결을 유지하는 프로그램 필요)
대용량 데이터테이블 단위 복사병렬 덤프로 더 빠름
덤프 파일남지 않음남음 (백업으로도 활용)
  • 대시보드 표시: 내부적으로는 한 명령이지만 pg_subscription_rel의 테이블별 상태로 초기 복사(덤프) → CDC 따라잡기 → 실시간 동기화를 나눠 보여 줍니다.
  • 확장 아이디어: db-postgres Skill이 DB 크기를 보고 A와 B 중 하나를 고르게 합니다.

05전환 (switchover)

  1. 1
    쓰기 일시 정지
    PgBouncer: PAUSE app
    새 트랜잭션을 대기시킵니다. 연결은 유지되므로 앱에는 에러가 나지 않고 잠깐 느려질 뿐입니다. pool_mode = transaction이어야 빨리 끝납니다.
  2. 2
    마지막 변경 도착 확인
    pg-a에 marker 행 INSERT → pg-b에 나타날 때까지 대기
    변경은 커밋 순서대로 전달되므로 marker가 도착했다면 그 앞의 변경도 모두 도착한 것입니다. 지연량 숫자는 피드백 주기 때문에 늦게 갱신될 수 있습니다.
  3. 3
    정방향 복제 종료
    pg-b: DROP SUBSCRIPTION mig_sub
    pg-a의 슬롯도 함께 정리됩니다. 역방향보다 먼저 꺼야 변경이 양쪽을 오가는 루프가 생기지 않습니다.
  4. 4
    시퀀스 동기화
    pg-a의 시퀀스 값을 읽어 pg-b에 setval
    시퀀스 값은 복제되지 않습니다.
  5. 5
    역방향 복제 생성
    pg-b: CREATE PUBLICATION / pg-a: CREATE SUBSCRIPTION … (copy_data = false)
    데이터가 이미 같으므로 복사 없이 변경만 받습니다. 이것이 롤백 경로입니다.
  6. 6
    연결 전환 후 재개
    PgBouncer 대상을 pg-b로 변경 → RESUME app
    1번부터 여기까지가 쓰기 중단 시간이며, 목표는 2초 이하입니다.

06복제되지 않는 것과 운영상 주의점

항목대응
DDL시작 전에 스키마를 복사하고, 이전 중에는 DDL을 금지합니다.
시퀀스 값전환할 때 직접 동기화합니다.
Large Object사전 점검에서 사용 여부를 확인합니다.
PK 없는 테이블REPLICA IDENTITY FULL을 설정합니다.
슬롯이 WAL을 붙잡음구독자가 멈추면 pg-a 디스크가 계속 찹니다. 지연량에 경보를 걸고, 중단·실패 시 슬롯을 삭제하는 단계를 반드시 넣습니다.
TRUNCATE복제되지만 대상에 FK가 있으면 실패할 수 있습니다.

시나리오

  1. 정방향 전환: pg-a → pg-b
  2. 전환 후 롤백: pg-b에 쓴 데이터가 역방향 복제로 pg-a에 반영되는지 확인
  3. 장애 주입: 복제 중 pg-b를 멈췄다 재시작해서 따라잡는지, 그동안 pg-a의 WAL이 쌓이는지 확인
  4. 사전 점검: PK 없는 테이블을 잡아내는지 확인
