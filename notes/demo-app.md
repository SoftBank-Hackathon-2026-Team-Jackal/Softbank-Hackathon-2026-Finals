## 2. 앱 형태: 왜 AI 에이전트 채팅인가

데모 앱이 좋다는 기준을 먼저 정했다. **유실이 생기면 누구나 바로 알아챌 수 있고, 여러 사람이 동시에 참여하며, 이전 과정이 화면에 드러나야 한다.** 평가 대상은 플랫폼이므로 데모 앱에는 하루 이상 쓰지 않는다.

| 후보 | 장점 | 단점 | 결과 |
|---|---|---|---|
| 주문 앱 | 단순함 | 무중단이 "아무 일도 일어나지 않음"이라 체감되지 않음 | 탈락 |
| 사람 채팅 | 메시지가 빠지면 대화가 끊겨 바로 보임 | 심사위원이 계속 채팅을 치기 어려움 | 에이전트 채팅으로 발전 |
| 공동 픽셀 캔버스 | 시각 효과가 크고 쓰기 부하가 큼 | 의미 검증(대화 맥락)이 없음, 채팅과 함께 만들면 범위 초과 | 탈락 |
| 송금 앱 (잔액 불변식) | Jepsen bank 테스트처럼 정합성 증명력이 가장 강함 | 화면이 숫자뿐이라 장내 분위기를 만들기 어려움 | 탈락. 검증 패널 아이디어만 가져옴 |
| 실시간 멀티플레이 게임 | 참여 열기 최고 | 전환 순간의 쓰기 중단(수백 ms)이 화면 멈춤으로 드러남 | 탈락 |
| **AI 에이전트 채팅** | 사람 없이도 대화가 계속됨, 에이전트가 유실을 스스로 감지하고 이전을 실황 중계함, AI 활용 주제와 연결됨 | LLM API에 의존 | **채택** (API 실패 시 준비된 대사로 대체) |

**에이전트가 유실 감지기가 된다.** 에이전트는 앞 대화를 읽고 이어서 말하므로 메시지가 빠지면 맥락이 깨진다. 또 자기가 보낸 메시지가 저장 확인을 받고도 스트림에 나타나지 않으면 "내 메시지 어디 갔어요?"라고 말한다. 숫자 검증(영수증 대조)과 의미 검증(대화가 자연스럽게 이어지는가)이 동시에 일어난다.

**한국어 + 일본어 번역.** 처음에는 일본어로만 말하는 에이전트(ケンジ)를 두었으나, 다른 에이전트들까지 일본어로 따라가는 문제가 생겼다. 모두 한국어로 말하고 같은 호출에서 일본어 번역을 함께 생성해 말풍선 아래에 붙이는 방식으로 바꿨다. 번역 때문에 호출 수가 늘지 않는다.

## 3. 기술 선택

### 3.1 언어와 런타임

| 후보 | 이미지 크기 | 의존성 설치 | 멀티 아키텍처 빌드 | 결과 |
|---|---|---|---|---|
| Python (FastAPI + uv) | 150MB 안팎 | uv로 빠름 | QEMU 에뮬레이션 필요 | 플랫폼 쪽에 적합, 데모 앱에는 불리 |
| Node 24 | 150MB 안팎 | npm/pnpm | QEMU 필요 | 탈락 |
| Bun | 50~100MB | 내장 서버·Postgres 클라이언트로 의존성 0 가능 | Mac에서 교차 컴파일 가능 | 차점 |
| **Go** | **10~20MB** | pgx 하나 | **교차 컴파일 (`GOARCH`)**, `ko`로 Dockerfile 없이 빌드 | **채택** |
| Rust | 작음 | - | 교차 컴파일 설정 번거로움, 컴파일 느림 | 탈락 (4일 안에 학습 부담) |

결정 이유: Mac(arm64)에서 개발하고 x86 VM과 온프레미스에 배포하므로 **교차 컴파일이 쉬운 언어**가 빌드 시간에서 가장 유리하다.

### 3.2 프론트엔드

htmx를 검토했으나 채택하지 않았다. htmx는 서버에서 HTML 조각을 받아 바꿔 끼우는 상호작용 도구이고, 화면이 투박한 문제는 CSS로 해결할 부분이다. 또 이 화면은 SSE 재접속과 유실 검증 장부를 직접 다뤄야 해서 순수 JS가 더 단순하다. React는 Node 빌드 단계가 생겨 빌드 속도 이점이 사라지므로 데모 앱에는 쓰지 않는다 (플랫폼 대시보드는 React Flow 때문에 React + Vite).

## 4. 무중단을 위한 앱 설계

| 문제 | 해결 | 검토한 대안 |
|---|---|---|
| 로드 밸런서 가중치를 바꿔도 기존 연결은 옮겨지지 않음 | **SSE** 사용. 브라우저 `EventSource`가 끊기면 `Last-Event-ID`로 마지막 메시지 다음부터 이어 받음 | WebSocket: 재접속과 이어 받기를 직접 구현해야 함 |
| 서버가 503을 주면 `EventSource`가 영구히 닫힘 | 닫힌 경우 JS가 직접 다시 연결 | - |
| env-a와 env-b 앱이 동시에 떠 있을 때 서로의 메시지를 받아야 함 | **공유 DB를 150ms마다 조회**하는 방식을 메시지 버스로 사용 | `LISTEN/NOTIFY`: PgBouncer transaction 모드에서 동작하지 않고 논리 복제로도 전달되지 않음. Redis: 구성 요소 추가 |
| 동시 INSERT의 id 순서와 커밋 순서가 어긋나면 `id > 마지막 id` 조회가 늦게 커밋된 행을 건너뜀 | INSERT를 **advisory lock으로 직렬화** (채팅 쓰기량에서는 비용 무시 가능) | 시간 지연 창: 완전하지 않음 |
| 전환 중 전송 실패 시 재전송하면 중복 저장 | 클라이언트가 만든 `client_msg_id`에 UNIQUE + `ON CONFLICT DO NOTHING` | - |
| 유실 판단 기준 | `client_msg_id` 대조. 시퀀스는 중복 거부에도 번호를 소비하므로 id가 건너뛴 것은 유실이 아님 | - |
| PgBouncer transaction 모드와 prepared statement 충돌 | pgx를 simple protocol로 고정 | PgBouncer `max_prepared_statements` |
| DB 전환 중(PAUSE) 헬스 체크까지 실패하면 로드 밸런서가 모든 앱을 내림 | **헬스 체크는 DB를 확인하지 않음** | - |
| 앱 종료 시 연결 정리 | SIGTERM → 헬스 체크 503 → SSE 종료(다른 앱으로 재접속) → 3초 대기 → 진행 중인 요청 완료 후 종료 | - |
| 스키마 관리 | 앱이 시작할 때 `CREATE TABLE IF NOT EXISTS` 적용 (advisory lock). 테이블이 있으면 카탈로그를 바꾸지 않으므로 DDL 금지 구간에 재시작해도 안전 | DB init 스크립트: 앱과 인프라 저장소가 묶임 |
| 메시지가 어느 DB에 저장됐는지 표시 | `db_node` 컬럼 기본값을 `current_setting('app.node_name')`로. 기본값은 쓰기를 받은 서버에서 계산되고, 논리 복제는 값 자체를 옮기므로 원래 값이 유지됨. 노드 이름은 인프라 쪽에서 서버마다 설정 | - |

## 5. AI 에이전트

- 페르소나 4명: SRE봇(지연·롤백), PM봇(일정·격려), 보안봇(포트·권한·암호화), ケンジ(일본 지사 개발자)
- **실제 사용자와 같은 경로로만 접속한다.** DB에 직접 쓰면 이전 경로를 검증하지 못한다. 또 env-a·env-b 밖에서 실행해야 env-a를 지울 때 에이전트가 같이 죽지 않는다.
- 모델: `claude-haiku-5-5`, effort `low`. 4~5초에 한 마디면 시간당 약 $0.2 (Opus 5.5는 약 $6). `CHAT_MODEL`로 변경 가능.
- 대화 품질 조정 (첫 실행에서 발견):
  - 이름이 불린 에이전트가 항상 답하면 두 명끼리만 대화함 → 바로 답할 확률 60%, 최근 3번 안에 말한 에이전트는 덜 고름
  - 같은 주제를 맴돎 → 30% 확률로 새 화제 제시
  - 모델이 "이름: 내용"으로 쓰는 경우 이름표 제거
- API 키는 `agents/.env` (Git 제외). API 실패나 거부 시 준비된 대사로 대체. `--offline`이면 API 없이 동작.
- 쓰기 부하용으로는 약하다 (몇 초에 한 건). 쓰기 부하는 PoC의 loadgen이 맡고, 에이전트는 눈에 보이는 층을 맡는다.

## 8. 빌드 시간 측정

### 8.1 결과

로컬은 캐시가 없는 BuildKit 빌더를 새로 만들어 깨끗한 CI 러너와 같은 조건으로 측정했다.

| 방식 | 조건 | 소요 시간 |
|---|---|---|
| **GitHub Actions + ko** | 깨끗한 러너, amd64 + arm64, GHCR push 포함 | **31초** (ko build 14초) |
| GitHub Actions + ko (2회차) | Go 캐시 적중 | 34초 (ko build 17초) |
| Docker, arm64 하나 | 캐시 없음 | 45초 |
| Docker, amd64 + arm64 (수정 전) | 캐시 없음, amd64를 QEMU로 컴파일 | 84초 |
| Docker, amd64 + arm64 (수정 후) | 캐시 없음, `--platform=$BUILDPLATFORM` 교차 컴파일 | **50초** |
| Docker, 코드 한 줄 수정 후 재빌드 | 캐시 있음 | **1.6초** |

### 8.2 해석

- Docker 콜드 빌드 50초 중 **37초는 `golang:1.24` 이미지(약 800MB) 다운로드**다. ko는 러너의 Go로 바로 컴파일하고 작은 distroless 베이스에 얹기만 하므로 이 시간이 없다.
- CI 2회차의 `ko build` 17초 내역: ko 시작과 베이스 이미지 확인 약 7.6초, **실제 컴파일(2개 아키텍처) 약 1.8초**, 레이어·SBOM push 약 4~5초. 컴파일은 이미 병목이 아니다.

### 8.3 더 줄일 수 있는 방법

| 방법 | 예상 효과 | 판단 |
|---|---|---|
| `go vet`을 별도 job으로 병렬 실행 | 약 4초 | 적용 예정 |
| `.ko.yaml` 베이스 이미지를 digest로 고정 | 1~2초 | 적용 예정 (재현성도 좋아짐) |
| SBOM 끄기 | 1~2초 | 하지 않음. 보안·거버넌스 시각화에서 이미지 구성 요소 스캔의 재료 |
| Go 캐시 끄기 | 0초 안팎 | 의미 없음 |

GitHub 호스티드 러너에서는 20초 안팎이 사실상 하한선이다.

### 8.4 결론

**이전 과정에서는 빌드하지 않는다.** CI가 push 시점에 이미지를 만들어 두고, env-b는 같은 digest를 pull한다. 데모에서 중요한 시간은 빌드가 아니라 **pull → 기동 → 헬스 체크 통과**까지의 시간이며, 이를 측정해 대시보드에 보여 주는 편이 효과가 크다.

## 9. 작업 중 발견한 문제

| 문제 | 원인 | 수정 |
|---|---|---|
| Postgres init 스크립트가 exit 126으로 실패 | 마운트한 `.sh` 파일을 실행 파일로 인식했으나 실행 권한 오류 | psql의 `\getenv`를 쓰는 `.sql` 파일로 대체 |
| `docker compose stop`이 약 1초 만에 앱을 강제 종료 | Compose 기본 대기 시간이 drain 시간(3초)보다 짧게 동작 | `stop_grace_period: 20s` 명시. 수동 SIGTERM으로 drain 순서 자체는 정상임을 확인 |
| 모든 에이전트가 일본어로 대화 | 일본어 페르소나가 먼저 말하자 나머지가 따라감 | 전원 한국어 + 번역 필드로 구조 변경 |
| 두 에이전트끼리만 대화 | 이름이 불리면 항상 그 에이전트가 답함 | 확률과 최근 발언자 회피 |
| 멀티 아키텍처 Docker 빌드가 느림 | amd64 컴파일을 QEMU 안에서 실행 | 빌드 머신 아키텍처에서 교차 컴파일 |
