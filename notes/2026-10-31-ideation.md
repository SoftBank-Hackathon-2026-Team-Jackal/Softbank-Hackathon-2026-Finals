## 3. 채택한 방향

### 한 줄 요약

**Scanner가 인프라를 지도로 만들고, 도메인별 Skill이 이전 계획을 세우고, 샌드박스에서 검증한 뒤 승인받으면, 트래픽과 데이터까지 무중단으로 옮겨 주는 플랫폼**

### 최초 제안 (팀 아이디어)

```
Scanner가 인프라 구조를 map → Skills가 무엇으로 바꿀지 계획 → 승인 → 새로 띄움
```

- Skill = **도메인별 지식 묶음** (DB, Security 등). 각 Skill이 자기 영역의 이전 계획을 스스로 세움
- "새로 띄움" = 인프라 생성뿐 아니라 **트래픽 전환과 데이터 이전(DB dump + CDC)까지** 포함

### 논의 후 보완한 전체 흐름

```
Scan → Map → Plan(도메인 Skills + 오케스트레이터) → Rehearse(샌드박스) → Approve
     → Provision → Phase A(컴퓨트 전환) → Phase B(DB 전환 + 역방향 CDC) → Verify / Rollback
```

| 단계 | 역할 | 대응하는 데모 장면·심사 항목 |
|---|---|---|
| Scan / Map | 인프라와 코드 의존성을 수집해 **클라우드 중립적인 공통 모델**로 표현. IAM·암호화·공개 여부도 함께 수집 | 보안 시각화(장면 2), 추상화(클라우드 30점) |
| Plan | 도메인 Skill이 각자 계획 → 오케스트레이터가 하나의 실행 순서(DAG)로 합치고 충돌 검사 | 추상화, 확장성(독창성) |
| Rehearse | AI 에이전트가 샌드박스에 계획을 적용·테스트하고 깨지는 코드를 수정 | AI 샌드박스(장면 3), AI 활용 10점 |
| Approve | 사람이 계획 + 검증 결과 + 수정 diff를 보고 승인 | "AI에게 어디까지 맡길 수 있는가"에 대한 답 |
| Provision | 승인된 IaC로 새 환경 생성 | |
| Phase A / B | 컴퓨트 전환 → DB 전환 (아래 상세) | 무중단 이전(장면 1), 롤백 |
| Verify / Rollback | 오류율·지연 감시, 문제 시 자동 롤백 | 프로덕션 운영 설계 |

## 4. 핵심 설계 논점

### 4.1 Skill 설계

- **도메인 분리 이유:** 실제 조직에서도 DB·보안·네트워크 담당이 각자 이전 계획을 세움. Skill을 추가하면 새 환경·새 리소스를 지원할 수 있다는 확장성 이야기가 가능함
- 예상 Skill 목록 (초안): Compute, DB, Network, Security(IAM·암호화), Secrets, (선택) AI 리소스
- **Skill 간 의존성:** 예) DB Skill이 "새 DB를 private subnet에 둔다" → Network·Security Skill이 이에 맞춰야 함 → **오케스트레이터**가 계획을 DAG로 합치고 충돌을 검사해야 함
- **출력 형식:** 자연어 계획이 아니라 **IaC 코드(Terraform 등) + 단계별 런북**의 구조화된 형식 → 승인 화면에서 diff 표시가 가능하고 그대로 실행 가능

### 4.2 트래픽 분할과 DB 쓰기 충돌 (가장 중요한 논점)

- **문제:** 트래픽을 10%만 새 환경으로 보냈을 때 새 앱이 새 DB에 쓰면, 새 DB는 아직 CDC로 복제받는 중이므로 양쪽에 서로 다른 쓰기가 쌓이는 **split-brain**이 발생함
- **해결:** 컴퓨트 전환과 DB 전환을 분리하는 2단계 구조

```
Phase A: 컴퓨트 전환
  새 환경 앱 기동 → 새 앱도 일단 "기존 DB"에 연결
  트래픽 10% → 50% → 100% (오류율 상승 시 즉시 롤백)
  이 동안 CDC로 새 DB는 계속 따라잡는 중

Phase B: DB 전환 (switchover)
  CDC 지연(lag) 0 확인 + 행 수·체크섬 검증
  수 초간 쓰기 일시 정지 → 시퀀스 동기화 → 새 DB 승격
  앱 연결을 새 DB로 전환 → 쓰기 재개
  역방향 CDC(새 DB → 기존 DB) 시작 ← 롤백 보험
```

- **역방향 CDC**가 핵심 어필 포인트: DB 전환 후에도 기존 환경으로 돌아갈 길이 남아 있음 → "롤백까지 설계했다"

### 4.3 데이터 이전 방식 (dump + CDC)

- dump만 하면 그 사이의 쓰기가 유실되거나 서비스를 멈춰야 함 → **CDC 필수**

| 선택지 | 장점 | 단점 | 결정 |
|---|---|---|---|
| PostgreSQL 논리 복제 (publication/subscription) | 기본 기능, 초기 복사와 변경 스트리밍을 함께 처리 → dump와 CDC 사이 시점 정합성 자동 해결, 구성 요소 적음 | PostgreSQL 간에만 사용 가능 | **우선 채택 (검증 필요)** |
| Debezium + Kafka | 범용적, 이종 엔진 지원 | 띄울 구성 요소가 많아 이틀 안에 안정화하기 어려움 | 대안으로 기록 |
| 클라우드 관리형 (AWS DMS, GCP DMS) | 관리 부담 적음 | 특정 클라우드에 종속 → 테마("Beyond Lock-In")와 어긋남, 역방향 구성이 어려움 | 대안으로 기록 |

- **DB 엔진:** 양쪽 모두 PostgreSQL로 통일. 이종 엔진 이전(MySQL → PostgreSQL)은 스키마 변환 문제까지 생겨 범위 밖으로 둠

## 5. 위험 요소

| 위험 | 내용 | 대응 |
|---|---|---|
| 관리형 DB의 논리 복제 설정 | RDS는 `rds.logical_replication` 파라미터 + 재부팅, Cloud SQL은 `cloudsql.logical_decoding` 플래그 필요 | **가장 먼저 실제로 검증** |
| 클라우드 간 네트워크 연결 | 복제를 위해 두 DB가 서로 통신해야 함 (VPN, 공개 IP + 허용 목록, SSL 등) | 위와 함께 초기에 검증 |
| Scanner 범위 폭발 | 임의의 인프라를 전부 스캔하는 것은 이틀 안에 불가능 | 데모 앱이 쓰는 리소스(컴퓨트, DB, 스토리지, 시크릿, AI 서비스)만 지원. 입력 소스는 Terraform state, 클라우드 API(AWS Resource Explorer, GCP Cloud Asset Inventory), 소스 코드의 SDK import 분석으로 한정 |
| 시퀀스·스키마 변경 | 논리 복제는 시퀀스 값과 DDL을 복제하지 않음 | switchover 시 시퀀스 동기화 단계 포함, 이전 중 DDL 금지 |

## 6. 우선순위

1. **DB 이전 경로(CDC + switchover + 역방향 CDC)를 가장 먼저 실제로 동작시킨다.** 데모에서 가장 강력한 장면이면서 기술적 위험도 가장 크기 때문
2. Phase A 트래픽 전환과 자동 롤백
3. Scan/Map의 공통 모델 설계 + 보안 시각화
4. Skill + 오케스트레이터 + 승인 화면
5. Rehearse(샌드박스)에서 AI 에이전트의 점검·수정

## 8. 후속 결정 (같은 날 이어서 논의)

| 주제 | 결정 | 검토한 대안과 이유 |
|---|---|---|
| CDC 방식 | PostgreSQL 16 논리 복제 (`copy_data = true`로 초기 복사와 CDC를 한 번에) + PgBouncer `PAUSE`로 전환 순간 제어 | 대용량이면 스냅샷 기반으로 dump와 CDC를 명시적으로 분리하는 방식으로 전환 가능. 정방향 구독을 먼저 끄고 역방향을 만들어 복제 루프를 방지 |
| 환경 간 네트워크 | **WireGuard** | 공개 IP + 허용 목록은 DB가 인터넷에 노출됨. 클라우드 간 VPN은 구성이 오래 걸리고 온프레미스 PC에 적용하기 어려움. WireGuard는 NAT 뒤의 PC까지 같은 방식으로 연결 가능 |
| DB 배치 | MVP는 VM에 직접 띄운 PostgreSQL, 관리형 DB는 확장 | 관리형 DB는 구독 권한과 VPC 연결 제약이 서비스마다 다름. 직접 띄운 구성은 온프레미스와 같아서 그대로 온프레미스 지원이 됨 |
| Skill 구성 | MVP 5개: `db-postgres`, `compute`, `network-wireguard`, `security-iam`, `app-code-adapter` | `app-code-adapter`를 추가한 이유: 인프라만 옮기면 앱 코드의 클라우드 SDK 호출이 깨짐. AI 샌드박스 장면을 가장 자연스럽게 보여 줌 |
| Skill 설계 원칙 | 판단은 LLM, 순서가 중요한 실행은 검증된 스크립트 | 모든 것을 LLM이 생성하면 switchover처럼 순서 하나에 데이터가 유실되는 작업을 안전하게 맡길 수 없음 |
| 승인 방식 | 대시보드의 승인 화면 (표 + 다이어그램), 승인 게이트 2개 (Phase A 전, Phase B 직전) | 한 번 승인으로 끝까지 실행하면 되돌리기 가장 어려운 DB 전환 직전에 사람이 판단할 기회가 없음 |
| Git | 계획·IaC·코드 수정·승인 기록의 장부. 실행은 Executor가 담당 | PR 페이지에서 승인하면 데모 화면이 갈라짐. GitHub Actions 실행(GitOps)은 실시간 표시와 단계별 판단이 어려움 |
| 대시보드 | 우선순위 1: 실시간 이전 현황, 승인 화면 / 2: Map / 3: 개요, 이력 | 최종 발표가 슬라이드 금지라서 대시보드가 발표 화면이 됨. 범위가 커지기 쉬워 우선순위를 둠 |

상세 설계는 [MVP 설계](./mvp.md)에 정리함.

## 9. CDC 수단 결정 (같은 날 이어서 논의)

| 주제 | 결정 | 검토한 대안과 이유 |
|---|---|---|
| CDC 수단 | **PostgreSQL 내장 논리 복제** | Debezium + Kafka: 변경을 읽는 원리는 같지만 Kafka, Connect, Sink 커넥터를 추가로 띄워야 하고, Sink에서 트랜잭션 경계가 흐려지기 쉬우며, 역방향 파이프라인도 따로 필요함. 이종 DB 이전으로 확장할 때 다시 검토 |
| 덤프 + CDC | **방법 A:** 스키마만 `pg_dump`, 데이터는 `copy_data = true`로 초기 복사와 CDC를 자동 연결 | **방법 B:** 슬롯 생성 시 스냅샷을 내보내고 `pg_dump --snapshot`으로 덤프 후 `copy_data = false`. 병렬 덤프로 대용량에 유리하지만 스냅샷 유지용 연결 관리가 필요해 구현이 복잡함 → 대용량 경로로 문서화, 시간이 남으면 Skill이 DB 크기를 보고 선택 |
| 전환 완료 판단 | marker 행이 pg-b에 도착했는지 확인 | 지연량 숫자로 판단: 구독자 피드백이 주기적으로만 전송되어 늦게 갱신될 수 있음 |
| 대시보드 표시 | 초기 복사(덤프) → CDC 따라잡기 → 실시간 동기화로 단계 분리 | `pg_subscription_rel` 상태로 구분 가능 |

상세 설계는 [CDC 설계](./cdc.md)에 정리함.
