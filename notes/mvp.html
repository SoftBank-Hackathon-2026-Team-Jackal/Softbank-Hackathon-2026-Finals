Beyond Lock-In MVP 설계

가동 중인 웹 앱을 스캔해 지도로 만들고, 도메인별 Skill이 이전 계획을 세우고, 샌드박스에서 검증해 승인받으면, 트래픽과 DB(dump + CDC)까지 무중단으로 다른 환경에 옮기는 플랫폼입니다.

가볍게 만들되, 한 경로는 끝까지 실제로 동작하게 합니다. 넓이보다 깊이를 우선합니다.

01MVP 범위

포함

  • 대표 경로 하나: 환경 A의 VM → 환경 B의 VM (다른 클라우드 또는 온프레미스 PC)
  • 예선 앱 재사용: 컨테이너 1개 + PostgreSQL 16
  • 양쪽 모두 VM에 직접 띄운 PostgreSQL, 논리 복제로 CDC
  • WireGuard 메시로 환경 간 사설망
  • HAProxy 가중치 전환 + DB 앞단 PgBouncer
  • 보안은 읽기 전용 점검과 시각화
  • Skill 기반 계획 + 샌드박스 코드 수정·테스트

제외 · 확장 후보

  • 관리형 DB(RDS, Cloud SQL) 이전: 설정 차이만 문서화
  • 이종 DB 엔진, 오브젝트 스토리지, AI 리소스 이전
  • 비용 최적화
  • 보안 문제의 자동 수정
  • 3개 이상 환경의 동시 관리

Skills (MVP 5개)

Skill판단 (LLM)실행 (검증된 스크립트)
db-postgres사전 점검 결과 해석, 위험 식별 (PK 없는 테이블 등), 대상 사양precheck.sql, start_replication.sh, check_lag.sql, verify_checksum.py, switchover.sh, reverse_replication.sh
compute대상 VM 사양, 환경 변수 매핑, 헬스 체크 경로Terraform 모듈, deploy_container.sh, healthcheck.sh
network-wireguard주소 대역, 피어 구성, 방화벽 규칙, 트래픽 전환 단계와 롤백 조건wg_keygen.sh, wg0.conf 템플릿, haproxy_set_weight.sh
security-iam보안 기준선 평가, 이전 전후 비교baseline_check.py (공개 포트, TLS, 권한, 평문 시크릿)
app-code-adapter클라우드 SDK 호출을 찾아 대상 환경에 맞는 수정안 작성샌드박스에서 테스트 실행

판단은 LLM이 하고, 순서가 중요한 실행은 검증된 스크립트가 합니다. 이것이 “AI에게 어디까지 맡길 수 있는가”에 대한 팀의 답입니다.

계획 조각 공통 계약

domain: db
mapping:   [{ from: env-a/app-db, to: env-b/app-db, reason: "..." }]
prechecks: [{ id: wal-level, check: "SHOW wal_level = logical" }]
requires:  [network.tunnel(env-a, env-b)]       # 다른 도메인에 요구
provides:  [db.endpoint(env-b)]                  # 다른 도메인에 제공
steps:
  - { id: db-replicate, depends_on: [network.tunnel-up],
      action: ..., verify: ..., rollback: ... }  # 모든 단계는 검증·롤백과 짝
risks: ["audit_log에 PK 없음 → REPLICA IDENTITY FULL 필요"]

Orchestrator · Rehearse · Approve · Executor

구성 요소역할
OrchestratorMap을 도메인별로 나눠 Skill에 전달하고, 계획 조각을 requires/provides로 연결해 DAG로 만든 뒤 위상 정렬합니다. 짝 없는 요구, 순환 의존, 상충하는 계획이 있으면 해당 Skill에 재계획을 요청합니다.
Rehearse대상 환경을 흉내 낸 격리 컨테이너에서 앱을 새 설정으로 띄우고, app-code-adapter가 수정한 코드로 테스트를 돌립니다. 실패하면 횟수 제한 안에서 수정을 반복합니다.
Approve UIMap(보안 점검 결과를 색으로 표시), 실행 DAG, Skill별 근거, 코드 diff, 위험 목록을 보여 주고 승인 또는 거절을 받습니다.
ExecutorDAG 순서대로 action과 verify를 실행합니다. 실패하면 이미 실행한 단계의 rollback을 역순으로 실행하고, 모든 로그를 UI에 실시간으로 표시합니다.

04네트워크와 데이터 이전

WireGuard

  • network-wireguard Skill이 키 쌍을 만들고 wg0.conf를 배포합니다.
  • PostgreSQL 5432 포트는 WireGuard 주소에서만 열고 공개 인터페이스에서는 닫습니다. 이 변화가 보안 지도에 그대로 반영됩니다.
  • 온프레미스 PC가 NAT 뒤에 있으면 PC 쪽에 PersistentKeepalive를 설정해 먼저 연결을 엽니다.

Phase A · 트래픽 전환

  1. env-b에 앱을 띄우고, DB 연결은 env-a의 PgBouncer로 둡니다.
  2. HAProxy 가중치를 10 → 50 → 100으로 올리며 단계마다 오류율과 지연을 확인합니다.
  3. 임계값을 넘으면 가중치를 즉시 되돌립니다.

Phase B · DB 전환

  1. 지연량 0, 행 수와 체크섬 일치를 확인합니다.
  2. PgBouncer PAUSE → 정방향 구독 비활성화 → 시퀀스 동기화
  3. 역방향 복제를 만듭니다 (copy_data = false).
  4. PgBouncer 대상을 env-b DB로 바꾸고 RESUME합니다.

05승인 화면 · Git · 대시보드

승인 화면은 사람과 AI가 만나는 유일한 지점입니다. 대시보드는 보고 판단하고 실행을 지켜보는 화면이고, Git은 무엇을 왜 바꿨는지 남기는 장부입니다.

승인자가 답을 얻어야 하는 질문

승인자의 질문보여 줄 방식
무엇이 어떻게 바뀌는가?Before / After 지도 (추가·변경·삭제를 색으로 표시)
어떤 순서로 실행되는가?실행 DAG (Skill별 레인, Phase 구분, 승인 게이트 표시)
왜 이렇게 바꾸는가?매핑 표 (기존 → 대상, 담당 Skill, 근거)
무엇이 위험한가?위험 표 (심각도, 대응 방법, 확인 체크)
실제로 검증했는가?리허설 결과 (테스트 결과, 코드 diff)
문제가 생기면 되돌릴 수 있는가?단계마다 롤백 가능 여부 표시
서비스가 얼마나 멈추는가?요약 바 (예상 쓰기 중단 시간)

승인 화면 와이어프레임

┌─────────────────────────────────────────────────────────────────────┐
│ env-a (AWS) → env-b (GCP)   쓰기 중단 예상 ~1초   롤백 가능 ●        │
│ 리허설 통과 12/12   위험 High 1 · Med 2   계획 v3 (a91f…)            │
├──────────────────────────────┬──────────────────────────────────────┤
│  Before / After 지도          │  실행 DAG                             │
│  [app]──[db 5432 공개]  →    │  network ─●─────────────────────      │
│  [app]──[db 사설망] (초록)    │  db       ───●(복제)───────●(전환)    │
│  + 추가  ~ 변경  − 삭제       │  compute  ──────●(기동)               │
│                              │  traffic  ─────────●10→50→100%       │
│                              │          ▲ 승인 게이트 1  ▲ 게이트 2   │
├──────────────────────────────┴──────────────────────────────────────┤
│ [매핑]  [위험 3]  [리허설 · 코드 diff]  [실행 로그]                    │
├─────────────────────────────────────────────────────────────────────┤
│ ☐ High 위험 1건을 확인했습니다          [거절]  [Phase A까지 승인]     │
└─────────────────────────────────────────────────────────────────────┘
  • 승인 게이트 2개: 게이트 1은 Phase A 시작 전, 게이트 2는 Phase B(DB 전환) 직전입니다. 게이트 2에서는 실제 CDC 지연량과 체크섬 결과를 보고 다시 판단합니다.
  • High 위험은 확인 체크 필수: 체크하지 않으면 승인 버튼이 비활성화됩니다.
  • 승인은 계획 버전(커밋 해시)에 묶습니다. 재계획되면 기존 승인은 무효가 됩니다.
  • 표와 다이어그램은 구조화된 데이터를 그대로 렌더링합니다. LLM은 맨 위의 짧은 자연어 요약만 작성하므로, 화면과 실제 실행 내용이 정확히 일치합니다.

Git: 계획과 승인의 장부

migrations/2026-11-07-env-a-to-env-b/
├── map.before.yaml        # Scanner 결과
├── plan.yaml              # 오케스트레이터가 합친 DAG
├── skills/                # Skill별 계획 조각
├── terraform/             # 생성될 IaC
├── runbook.md             # 계획에서 자동 생성한 사람용 런북
└── rehearsal/             # 리허설 테스트 결과
  • 계획이 만들어지면 이전 작업마다 브랜치와 PR을 만듭니다. 재계획은 새 커밋이므로 계획 버전이 곧 커밋 해시입니다.
  • app-code-adapter가 고친 앱 코드는 앱 저장소에 별도 PR로 올립니다.
  • 승인은 대시보드에서 하고, 플랫폼이 GitHub API로 PR 승인·병합과 승인 기록(승인자, 계획 해시, 시각)을 남깁니다.
  • 실행은 Git에 맡기지 않고 Executor가 맡습니다.
검토한 대안채택하지 않은 이유
GitHub PR 페이지에서 직접 승인데모 화면이 두 곳으로 갈라지고, 승인용 표와 다이어그램을 보여 줄 수 없습니다.
GitHub Actions로 실행 (GitOps)실행 상태를 실시간으로 보여 주기 어렵고, CDC 지연량을 보며 다음 단계로 넘어가는 판단을 넣기 어렵습니다.

대시보드 화면

최종 발표는 슬라이드가 금지되고 설계 문서와 데모로만 진행되므로, 대시보드가 사실상 발표 화면입니다.

우선순위화면내용데모 장면
1실시간 이전 현황트래픽 가중치, CDC 지연량, p99 지연, 양쪽 DB 행 수, 단계별 실행 로그가동 중인 앱의 이전
1승인 화면위의 구성AI 샌드박스 점검·수정
2Map환경과 리소스 그래프, 보안 점검 결과를 색으로 표시보안 시각화
3개요환경별 상태와 보안 점수 카드
3이력지난 이전 작업 목록, 각 작업의 Git PR 링크거버넌스

백엔드가 HAProxy 통계, pg_stat_* 뷰, Executor 로그를 수집해 SSE나 WebSocket으로 전송합니다. 우선순위 1인 두 화면을 먼저 완성합니다.

09미결정 사항

  • 대표 이전 경로의 env-a와 env-b를 실제로 무엇으로 할지 (예: AWS → GCP, AWS → 온프레미스 PC)
  • 예선 시스템의 언어와 구조, 재사용 범위
  • Skill별 담당자
  • HAProxy 위치: env-a에 두면 env-a가 단일 장애 지점이 됩니다. MVP에서는 허용하고 한계로 명시합니다.
  • 샌드박스 범위: 코드 테스트만 할지, 인프라 적용까지 흉내 낼지
