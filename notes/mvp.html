Beyond Lock-In MVP 설계

가동 중인 웹 앱을 스캔해 지도로 만들고, 도메인별 Skill이 세운 이전 계획을 샌드박스에서 검증합니다. 사람이 승인하면 트래픽과 DB를 덤프와 CDC로 다른 환경에 무중단으로 옮깁니다.

기능은 가볍게 만들되, 대표 경로 하나는 처음부터 끝까지 실제로 동작하게 만듭니다.

01MVP 범위

포함

  • 대표 경로 하나: 환경 A의 VM → 환경 B의 VM (다른 클라우드 또는 온프레미스 PC)
  • 예선 앱 재사용: 컨테이너 1개 + PostgreSQL 16
  • 양쪽 모두 VM에 직접 띄운 PostgreSQL, 논리 복제 기반 CDC
  • WireGuard 메시로 구성한 환경 간 사설망
  • HAProxy 가중치 기반 트래픽 전환, DB 앞단의 PgBouncer
  • 보안은 읽기 전용 점검과 시각화까지
  • Skill 기반 계획, 샌드박스에서 코드 수정과 테스트

제외 및 확장 후보

  • 관리형 DB(RDS, Cloud SQL) 이전: 설정 차이만 문서화
  • 이종 DB 엔진, 오브젝트 스토리지, AI 리소스 이전
  • 비용 최적화
  • 보안 문제의 자동 수정
  • 3개 이상 환경의 동시 관리

steps:
  - { id: db-replicate, depends_on: [network.tunnel-up],

risks: ["audit_log에 PK 없음 → REPLICA IDENTITY FULL 필요"]

Orchestrator, Rehearse, Approve, Executor

구성 요소역할
OrchestratorMap을 도메인별로 나눠 Skill에 전달하고, 계획 조각을 requires와 provides로 연결해 DAG로 만든 뒤 위상 정렬합니다. 짝이 없는 요구, 순환 의존, 상충하는 계획이 있으면 해당 Skill에 다시 계획하도록 요청합니다.
Rehearse대상 환경을 흉내 낸 격리 컨테이너에서 앱을 새 설정으로 띄우고, app-code-adapter가 수정한 코드로 테스트를 실행합니다. 테스트가 실패하면 정해진 횟수 안에서 수정을 반복합니다.
Approve UIMap(보안 점검 결과를 색으로 표시), 실행 DAG, Skill별 근거, 코드 diff, 위험 목록을 보여 주고 승인 또는 거절을 받습니다.
ExecutorDAG 순서대로 action과 verify를 실행합니다. 실패하면 이미 실행한 단계의 rollback을 역순으로 실행하고, 모든 로그를 UI에 실시간으로 표시합니다.

04네트워크와 데이터 이전

WireGuard

  • network-wireguard Skill이 키 쌍을 만들고 wg0.conf를 배포합니다.
  • PostgreSQL 5432 포트는 WireGuard 주소에서만 열고 공개 인터페이스에서는 닫습니다. 포트를 닫은 결과는 보안 지도에 그대로 반영됩니다.
  • 온프레미스 PC가 NAT 뒤에 있으면 PC 쪽에 PersistentKeepalive를 설정해 먼저 연결을 엽니다.

Phase A: 트래픽 전환

  1. env-b에 앱을 띄우고, DB 연결은 env-a의 PgBouncer로 둡니다.
  2. HAProxy 가중치를 10 → 50 → 100으로 올리며 단계마다 오류율과 지연을 확인합니다.
  3. 임계값을 넘으면 가중치를 즉시 되돌립니다.

Phase B: DB 전환

  1. Phase A 이전부터 논리 복제(CDC)로 새 DB가 계속 따라잡고 있습니다.
  2. PgBouncer PAUSE로 쓰기를 잠깐 멈추고, 마지막 변경이 도착했는지 확인합니다.
  3. 정방향 복제를 끄고 역방향 복제를 만든 뒤, 대상을 env-b DB로 바꿔 RESUME합니다.
  4. 자세한 원리와 6단계 절차는 바로 아래 05 섹션에 있습니다.

05CDC 쉽게 이해하기

CDC(Change Data Capture)는 DB에서 일어나는 변경(INSERT, UPDATE, DELETE)을 실시간으로 잡아서 다른 DB에 똑같이 반영하는 기술입니다. 가동 중인 DB를 멈추지 않고 옮기려면 꼭 필요합니다.

왜 덤프만으로는 안 되는가

덤프만 할 때

  • 덤프를 뜨는 동안에도 앱은 계속 데이터를 씁니다.
  • 덤프 이후에 들어온 쓰기는 새 DB에 없습니다.
  • 유실을 막으려면 덤프부터 복원까지 서비스를 멈춰야 합니다. 데이터가 크면 수십 분 이상 걸립니다.

덤프 + CDC

  • 기존 데이터는 한 번 복사하고(덤프), 그 이후의 변경은 CDC로 계속 따라갑니다.
  • 새 DB가 거의 실시간으로 기존 DB와 같은 상태를 유지합니다.
  • 멈추는 시간은 마지막 전환 순간의 1~2초뿐입니다.

어떻게 변경을 잡아내는가: WAL

PostgreSQL은 데이터를 바꿀 때 테이블보다 WAL(Write-Ahead Log)이라는 로그에 먼저 기록하고, 각 기록에 LSN이라는 위치 번호를 붙입니다. CDC는 이 WAL을 읽어서 새 DB에 순서대로 재생합니다. 이 프로젝트에서는 별도 도구 없이 PostgreSQL에 내장된 논리 복제(logical replication) 기능을 씁니다.

덤프와 CDC가 이어지는 방식

실제로는 아래 명령 몇 줄로 덤프와 CDC가 함께 시작됩니다. copy_data = true가 데이터 덤프 역할을 하고, 복사가 끝나면 자동으로 CDC로 넘어갑니다.

# 1. 스키마만 덤프 (테이블 구조 변경은 복제되지 않으므로 먼저 옮김)
pg_dump --schema-only "$PG_A" | psql "$PG_B"

-- 2. pg-a: 어떤 테이블의 변경을 내보낼지 지정
CREATE PUBLICATION mig_pub FOR ALL TABLES;

-- 3. pg-b: 구독 생성 → 슬롯 생성, 초기 복사, CDC가 이어서 진행
CREATE SUBSCRIPTION mig_sub
  CONNECTION 'host=10.100.0.1 dbname=app user=replicator'
  PUBLICATION mig_pub
  WITH (copy_data = true);

동기화가 얼마나 뒤처졌는지는 아래처럼 측정하며, 대시보드의 CDC 지연 그래프가 이 값입니다.

지연량 = pg-a의 현재 WAL 위치 − 슬롯이 확인받은 위치

전환 (switchover) 6단계

  1. 1
    쓰기 일시 정지
    PgBouncer: PAUSE app
    새 트랜잭션을 대기시킵니다. 연결은 유지되므로 앱에서는 오류가 발생하지 않고 응답만 잠깐 느려집니다. pool_mode = transaction이어야 일시 정지가 빨리 끝납니다.
  2. 2
    마지막 변경 도착 확인
    pg-a에 marker 행 INSERT → pg-b에 나타날 때까지 대기
    변경은 커밋 순서대로 전달되므로 marker가 도착했다면 그 앞의 변경도 모두 도착한 것입니다. 지연량 숫자는 피드백 주기 때문에 늦게 갱신될 수 있습니다.
  3. 3
    정방향 복제 종료
    pg-b: DROP SUBSCRIPTION mig_sub
    pg-a의 슬롯도 함께 정리됩니다. 역방향보다 먼저 꺼야 변경이 양쪽을 오가는 루프가 생기지 않습니다.
  4. 4
    시퀀스 동기화
    pg-a의 시퀀스 값을 읽어 pg-b에 setval
    시퀀스 값은 복제되지 않습니다.
  5. 5
    역방향 복제 생성
    pg-b: CREATE PUBLICATION / pg-a: CREATE SUBSCRIPTION … (copy_data = false)
    데이터가 이미 같으므로 복사 없이 변경만 받습니다. 이 역방향 복제가 롤백 경로가 됩니다.
  6. 6
    연결 전환 후 재개
    PgBouncer 대상을 pg-b로 변경 → RESUME app
    1번부터 여기까지가 쓰기 중단 시간이며, 목표는 2초 이하입니다.

알아 둘 주의점

항목이유와 대응
테이블 구조 변경 (DDL)복제되지 않습니다. 시작 전에 스키마를 복사하고, 이전 중에는 구조 변경을 금지합니다.
시퀀스 값 (자동 증가 ID)복제되지 않습니다. 전환할 때 직접 맞춥니다.
PK 없는 테이블UPDATE와 DELETE의 대상 행을 찾을 수 없습니다. REPLICA IDENTITY FULL을 설정합니다.
복제 슬롯새 DB가 멈추면 기존 DB에 WAL이 계속 쌓여 디스크가 가득 찹니다. 이전을 중단하면 슬롯을 반드시 삭제합니다.

더 자세한 내용(대용량용 덤프 방식, PoC 계획)은 notes/cdc.md에 있습니다.

  • 승인은 계획 버전(커밋 해시)에 묶습니다. 재계획되면 기존 승인은 무효가 됩니다.
  • 표와 다이어그램은 구조화된 데이터를 그대로 렌더링합니다. LLM은 맨 위의 짧은 자연어 요약만 작성하므로, 화면에 보이는 내용과 실제로 실행되는 내용이 정확히 일치합니다.

Git: 계획과 승인의 장부

migrations/2026-11-07-env-a-to-env-b/
├── map.before.yaml        # Scanner 결과
├── plan.yaml              # 오케스트레이터가 합친 DAG
├── skills/                # Skill별 계획 조각
├── terraform/             # 생성될 IaC
├── runbook.md             # 계획에서 자동 생성한 사람용 런북
└── rehearsal/             # 리허설 테스트 결과
  • 계획이 만들어지면 이전 작업마다 브랜치와 PR을 만듭니다. 재계획은 새 커밋이므로 계획 버전이 곧 커밋 해시입니다.
  • app-code-adapter가 고친 앱 코드는 앱 저장소에 별도 PR로 올립니다.
  • 승인은 대시보드에서 하고, 플랫폼이 GitHub API로 PR을 승인하고 병합한 뒤 승인 기록(승인자, 계획 해시, 시각)을 남깁니다.
  • 실행은 Git에 맡기지 않고 Executor가 담당합니다.
검토한 대안채택하지 않은 이유
GitHub PR 페이지에서 직접 승인데모 화면이 두 곳으로 갈라지고, 승인용 표와 다이어그램을 보여 줄 수 없습니다.
GitHub Actions로 실행 (GitOps)실행 상태를 실시간으로 보여 주기 어렵고, CDC 지연량을 보며 다음 단계로 넘어가는 판단을 넣기 어렵습니다.
