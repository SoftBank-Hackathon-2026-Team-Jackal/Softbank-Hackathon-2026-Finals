## 2. 트래픽 생성기

시연에는 실제 사용자가 없으므로 두 가지 트래픽 생성기를 함께 켭니다. AI 채팅 에이전트는 화면에 보여 줄 대화와 쓰기를 만들고, 부하 생성기는 게이트 판정에 필요한 요청 수를 채웁니다.

| 도구 | 하는 일 | 시연에서 쓰는 이유 |
|---|---|---|
| AI 채팅 에이전트 (demo-app `agents/chatbots.py`) | Claude(`claude-haiku-5-5`)로 만든 여러 인물이 3~6초마다 메시지를 보내고(POST), 스트림으로 서로의 메시지를 받습니다. 실패한 전송은 다시 보냅니다. 종료하면 보낸 메시지, 저장 확인, 스트림 수신, 유실, 중복 건수를 출력합니다. 비용은 시간당 약 $0.2입니다 | 서비스가 멈추지 않는 모습을 채팅창으로 보여 줍니다. 메시지마다 처리한 앱(`app_env`)과 저장한 DB(`db_node`)가 기록되어 전환 과정이 채팅창에 그대로 남습니다. 종료할 때 나오는 집계로 쓰기 손실 0건을 증명합니다 |
| 부하 생성기 (cloud-migration-platform `infra/demo/tools/demo-load.sh`) | 중계 서버 안에서 자기 입구로 `GET /api/messages`를 초당 20건 보냅니다. 요청은 가중치대로 원본과 대상으로 나뉩니다. 기본값으로 10분 뒤 저절로 꺼집니다 | 트래픽 게이트의 최소 요청 수와 그림자 리허설에 필요한 GET 요청을 채웁니다. 앱 장애 스위치가 걸리는 `/api/` 경로로 보내므로 장애가 게이트에 잡힙니다 |

실행 명령입니다.

```bash
# AI 채팅 에이전트 (demo-app 저장소의 agents 폴더, ANTHROPIC_API_KEY는 agents/.env)
uv run --env-file .env chatbots.py --url http://15.164.0.37:8080
uv run chatbots.py --url http://15.164.0.37:8080 --offline   # API 키가 없거나 모델 호출이 실패할 때

# 부하 생성기 (cloud-migration-platform 저장소의 infra/demo/tools 폴더)
aws sso login --profile cmp-aws-prod
MINUTES=15 bash demo-load.sh start    # 발표 직전에 켭니다
bash demo-load.sh status              # 켜져 있는지, 가중치와 누적 요청 수
bash demo-load.sh stop                # 발표가 끝나면 끕니다
```

- `demo-load.sh`는 Windows Git Bash 기준으로 작성되어 있습니다(AWS CLI 경로 `/c/Program Files/Amazon/AWSCLIV2/aws.exe`, `cygpath`). 맥에서 쓰려면 두 줄을 고치거나, 아래 명령으로 노트북에서 직접 보냅니다. 노트북에서 보내면 현장 네트워크 상태에 영향을 받습니다.

  ```bash
  URL=http://15.164.0.37:8080/api/messages
  while :; do seq 20 | xargs -P 20 -I{} curl -s -o /dev/null -m 3 "$URL"; sleep 1; done
  ```

- 채팅창에 보이는 라벨은 시점마다 다음과 같이 바뀝니다(11-08 `/api/stats`와 대상 앱 설정으로 확인).

## 3. 진행 방식: 계획 승인부터 라이브로 진행

분석부터 계획 승인 화면까지는 발표 직전에 미리 실행해 두고, 발표에서는 계획 승인부터 라이브로 진행합니다. 계획 승인 대기 시간은 7일이라서 발표 전에 멈춰 두어도 시간이 지나 실패하지 않습니다.

08:37 리허설에서 측정한 구간별 소요 시간은 다음과 같습니다.

| 구간 | 소요 시간 | 시연에서 다루는 방식 |
|---|---:|---|
| 분석 | 8초 | 미리 실행 |
| 요구사항 확인 클릭 | 34초 (사람) | 미리 실행 |
| 빌드, 샌드박스 검증, 레드팀 | 120초 (레드팀 약 95초) | 미리 실행 |
| 계획 승인 클릭 | 30초 (사람) | 라이브 시작점 |
| 구축 | 약 8초 | 라이브 |
| 데이터 이전 (사전 점검 12초, 초기 복사 5초, 그림자 리허설 55초 포함) | 계획 승인부터 DB 전환 승인 화면까지 111초 | 라이브 |
| DB 전환 승인 클릭 | 23초 (사람) | 라이브 |
| DB 전환 | 쓰기 중단 148.5ms | 라이브 |
| 트래픽 준비 | 10초 | 라이브 |
| 10% → 50% → 100% | 35초 (단계마다 관찰 10초와 클릭) | 라이브 |

- 처음부터 라이브로 진행하면 기계가 일하는 시간만 약 4분 45초입니다. 사람이 클릭하는 시간을 더하면 5분을 넘기고 장애 장면도 넣을 수 없습니다.
- 계획 승인부터 진행하면 100%까지 약 2분 40초가 걸립니다. 장애 주입과 재시도(약 50초)를 넣어도 5분 안에 끝납니다.
- 미리 실행한 사실은 발표에서 밝힙니다. 예: "분석과 샌드박스 검증은 3분 정도 걸려서 발표 직전에 돌려 두었습니다. 지금 보이는 화면은 그 실행의 실제 결과입니다."

## 4. 발표 전 준비 (발표 15분 전부터)

1. 이전 리허설이 남긴 상태를 초기화합니다(cloud-migration-platform 저장소).
   `SOURCE_CONTEXT=<원본 EKS context> TARGET_CONTEXT=<온프레미스 context> bash infra/demo/reset-rehearsal.sh`
2. 마지막 리허설이 끝난 뒤에는 worker와 노트북 Agent를 다시 배포하지 않습니다. 다시 배포하면 노트북 K3s 이미지와 빌드 캐시를 준비하는 시간이 시연 시간에 더해질 수 있습니다.
3. 노트북 온프레미스 Agent가 연결되어 있는지 확인합니다. 플랫폼 화면의 Pulse 위젯에 노드 CPU와 메모리가 보이면 연결된 상태입니다.
4. 원본 DB에 화면용 시드 데이터가 들어 있는지 확인합니다. 11-08 확인 결과 원본 DB에 표 13개와 시드 표시(`app_seed_info`)가 있습니다. 시드를 지우지 않습니다. 다시 넣어야 하면 데이터 이전을 시작하기 전에만 넣습니다(`infra/demo/tools/README.md`).
5. AI 채팅 에이전트를 켜고 계속 켜 둡니다(2장 명령). 채팅앱 탭에서 `aws-eks`, `pg-aws` 라벨이 붙은 새 메시지가 올라오는지 확인합니다.
6. 플랫폼에서 이전을 시작합니다.
   - "헤이 자칼" → "AWS에 있는 채팅 서비스를 온프레미스로 옮겨 줘" (인식이 안 되면 첫 화면에서 I 키로 의도를 넣고 O 키로 온프레미스 K3s를 고릅니다)
   - 저장소와 `.env` 파일을 고르고 시작 → 요구사항 확인 → **계획 승인 화면에서 멈춥니다** (약 3분)
7. 발표 직전에 부하 생성기를 켭니다(`MINUTES=15 bash demo-load.sh start`). 기본값은 10분 뒤 꺼지므로 너무 일찍 켜지 않고, `status`로 켜진 것을 확인합니다.
8. 브라우저 탭을 다음 순서로 엽니다. 플랫폼과 채팅앱을 화면 좌우에 나란히 띄우면 탭을 오가지 않아도 됩니다.
   1. Notion 「최종 발표 자료」
   2. 플랫폼 (계획 승인 화면, 오른쪽 Temporal 사이드바 열림)
   3. 채팅앱
9. 플랫폼 왼쪽 Tools 패널에서 장애 종류를 "오류 100%", 유지 시간을 60초로 골라 둡니다. 장애는 아직 켜지 않습니다.
10. 마이크로 "헤이 자칼"이 인식되는지 확인합니다. 인식이 안 되면 모든 단계를 버튼으로 진행합니다(버튼과 음성 명령은 같은 동작입니다).

## 7. 결정이 필요한 사항

1. **AI 수정과 레드팀 장면**: 결함이 없는 앱에서는 Fixer 수정 0건, 레드팀 발견 0건이 화면에 나옵니다. 그대로 보여 주고 설명으로 채울지, Fixer가 고칠 결함(DB 주소, readinessProbe, containerPort, HOST 등)을 넣은 브랜치로 시연할지 정해야 합니다. 결함 브랜치를 쓰면 미리 실행하는 시간이 늘어나고, 재시도 1회에 걸리는 시간은 아직 측정하지 않았습니다.
2. **안정화 구간 DB 롤백 문제(1장 1번)**: 시연 전에는 고치지 않습니다. 제대로 고치려면 되돌릴 때 대상 앱의 쓰기를 막는 처리(fencing)를 넣고 다시 전환할 때 풀어야 해서, 정방향 DB 전환 코드도 함께 바뀌고 배포와 리허설을 다시 해야 합니다. 고친 뒤에는 Slack 11-07 시나리오(100% 뒤 롤백으로 AWS 복귀, 다시 전환)를 쓸 수 있습니다.
3. **수동 단계 모드에서 재시도 확인**: 단계 중 자동 롤백 뒤 재시도는 11-07 실행(`b0d3f658`, `7ee771c4`)에서 동작했습니다. 하지만 수동 단계 모드가 들어간 11-08 01:57 이후에는 아직 확인하지 않았으므로, 마지막 리허설에서 5장 3:55~4:45 구간을 부하 생성기와 에이전트를 켠 상태로 한 번 돌려 봐야 합니다.
4. **역할 분담**: 발표자와 조작 담당(Tools 패널, 부하 생성기, 에이전트 터미널, 버튼)을 나눌지 정해야 합니다. `demo-load.sh`가 Windows Git Bash 기준이므로, 조작 담당 PC가 맥이면 스크립트를 고치거나 2장의 curl 명령을 씁니다.
