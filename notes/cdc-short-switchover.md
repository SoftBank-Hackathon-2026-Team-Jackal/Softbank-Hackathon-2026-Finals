# 전환 중단을 짧게 만드는 기술 정리 (2026-11-03)

> 관련 문서: [CDC 설계](./cdc.md) · [PoC 2단계 결과](../poc/cdc/cloud/README.md)

## 1. 목표

**쓰기 중단을 0으로 만드는 것이 아니라, 사용자가 느끼지 못할 만큼 짧게 만드는 것**이 목표입니다.

- 실패한 요청 0건은 유지합니다. 이미 달성했습니다.
- 쓰기 중단은 **0.1초 안팎**을 목표로 합니다. 평소 p99(약 90ms)와 구분되지 않는 수준입니다.
- 0으로 만들지 않는 이유가 있습니다. 비동기 복제에서는 옛 DB의 마지막 쓰기가 새 DB에 도착했는지 확인하기 전에 새 DB가 쓰기를 받으면 split-brain이 생깁니다. 따라서 아주 짧더라도 쓰기를 멈추는 순간이 필요합니다.

## 2. 출발점: 지금의 전환 (5GB, AWS ↔ GCP)

쓰기 중단은 1,304ms였습니다. PAUSE 명령을 보낸 순간부터 RESUME까지를 쟀습니다.

| 단계 | ms | 성격 |
|---|---|---|
| 진행 중 트랜잭션 대기 | 182 | 꼭 필요함. 그 순간 가장 긴 트랜잭션이 정함 |
| marker 도착 확인 | 280 | 비동기 복제라서 필요함 |
| 검증 (`max(id)`) | 262 | PAUSE 밖으로 뺄 수 있음 |
| 정방향 삭제 + 시퀀스 동기화 + 역방향 켜기 | 373 | 대부분 PAUSE 밖으로 뺄 수 있음 |
| PgBouncer 대상 변경 + RESUME | 207 | 꼭 필요하지만 더 줄일 수 있음 |

단계마다 psql을 새로 띄우면서 WireGuard 너머로 연결과 SCRAM 인증을 다시 하는 비용이 모든 단계에 섞여 있습니다.

## 3. 기술 목록

상태 표기: **검증됨**은 PoC에서 측정한 것, **미검증**은 아직 돌려 보지 않은 것입니다. 예상 효과는 미검증 항목의 추정치입니다.

### A. 전환 순간을 짧게

| # | 기술 | 방법 | 예상 효과 | 위험·대가 | 상태 |
|---|---|---|---|---|---|
| A1 | 역방향 구독 미리 만들기 | PAUSE 전에 `enabled = false`로 만들고 PAUSE 안에서는 `ENABLE`만 실행. 전환 전까지 대상에 들어오는 변경은 모두 복제로 받은 것이라 `origin = none`이 걸러 냄 | 0.5~0.7초 감소 | 꺼진 구독의 슬롯이 대상에서 WAL을 붙잡음 (짧은 시간) | **검증됨** (1.8초 → 1.0초) |
| A2 | 체크섬 병렬 계산 / 가벼운 검증 | 두 DB를 동시에 계산하고, 큰 DB는 PAUSE 안에서 `max(id)`만 비교 | 데이터 크기와 무관해짐 | 가벼운 검증은 행 단위 차이를 못 잡음 → 전환 직후 전체 검증으로 보완 | **검증됨** |
| A3 | **동기 복제 창** | 전환 직전 몇 초만 원본에 `synchronous_standby_names = '<구독 이름>'`을 설정. 커밋마다 대상 반영을 확인하므로 PAUSE 순간 대상이 이미 최신 | marker 대기(약 280ms) 제거 | 그 몇 초 동안 커밋마다 왕복 시간(3ms) 증가. 대상이 멈추면 원본 커밋이 막히므로 시간 제한과 자동 해제가 필요 | **검증됨** (변형: 동기 대기는 marker 커밋에만 걸고 앱은 `synchronous_commit = local`. 앱 커밋은 느려지지 않음) |
| A4 | 시퀀스 미리 올리기 | PAUSE 전에 대상 시퀀스를 원본 값 + 여유값(예: 10,000)으로 설정 | 시퀀스 동기화를 PAUSE 밖으로 | ID에 빈 구간이 생김 (기능상 문제 없음) | **검증됨** |
| A5 | 검증을 전환 직후로 | PAUSE 안에서는 검증하지 않고, 동기 복제(A3)가 보장한 상태를 믿음. 전환 직후 역방향 복제가 따라잡은 뒤 비교 | 검증(약 260ms) 제거 | 불일치를 전환 후에 발견하면 롤백으로 대응해야 함 | **검증됨** (PAUSE 안에서 두 DB의 스냅샷을 고정하고 RESUME 후 비교. 큰 DB는 `max(id)`만 비교, 전체 체크섬은 새 DB를 15초 동안 느리게 함) |
| A6 | 연결 하나로 유지 | 단계마다 psql을 띄우지 않고, 전환 프로그램이 원본, 대상, PgBouncer 관리 연결을 미리 열어 두고 SQL만 보냄 | 단계마다 수십 ms 감소 | 스크립트를 프로그램(Python 등)으로 바꿔야 함 | **검증됨** (`05_switchover_fast.py`) |
| A7 | 대상 연결 미리 열기 (pre-warm) | PgBouncer에 대상 DB 연결을 미리 만들어 두어, RESUME 직후 첫 요청이 연결을 새로 맺지 않게 함 | RESUME 직후 지연 감소 | PgBouncer 설정이 복잡해짐 | 미검증 |
| A8 | 긴 트랜잭션 대기 제한 | PAUSE가 `PAUSE_TIMEOUT_SEC` 안에 끝나지 않으면 전환을 포기하고 RESUME | 최악의 경우를 막음 | 전환이 미뤄질 수 있음 | **검증됨** (구현) |

A3~A7을 모두 적용하면 PAUSE 안에는 "진행 중 트랜잭션 대기"와 "대상 변경"만 남습니다. **예상 쓰기 중단은 50~100ms입니다.**

> **2026-11-04 결과:** A3~A6을 적용한 `05_switchover_fast.py`로 AWS ↔ GCP 쓰기 중단이 865ms / 874ms에서 **85ms / 134ms**로 줄었습니다 (약 450MB, 초당 200건, 에러 0, 유실 0). 자세한 내용은 [2단계 README](../poc/cdc/cloud/README.md#빠른-전환-2026-11-04)에 있습니다.

### B. 초기 복사를 빠르게

측정 결과 네트워크는 156MB/s였지만 복사는 13.2MB/s였습니다. 병목은 대상 DB가 행을 넣으면서 인덱스까지 갱신하는 작업입니다.

| # | 기술 | 방법 | 예상 효과 | 위험·대가 | 상태 |
|---|---|---|---|---|---|
| B1 | **PostgreSQL 17 `pg_createsubscriber`** | 물리 복제로 디스크 블록(인덱스 포함)을 그대로 복사한 뒤, 그 복제본을 논리 구독자로 바꿈 | 4.4GB 기준 335초 → 1분 안쪽 (네트워크 속도에 가까워짐) | 양쪽 메이저 버전이 같아야 함. 클러스터 전체를 복사함(DB 하나만 고를 수 없음). PoC 이미지를 16 → 17로 바꿔야 함 | **로컬 검증됨** (475MB 1.2초, 논리 복사 7초). 클라우드 미측정 |
| B2 | 인덱스를 나중에 만들기 | `pg_dump --section=pre-data`로 테이블만 만들고, 복사가 끝난 뒤 `post-data`(인덱스, 제약 조건)를 적용 | 복사 속도 향상 | 인덱스 생성 시간이 따로 들고, 그동안 대상에서 UPDATE/DELETE 적용이 느림 | 미검증 |
| B3 | 병렬 덤프 (방법 B) | 슬롯 생성 시 스냅샷을 내보내고 `pg_dump --snapshot -j N`으로 복사한 뒤 CDC만 시작 | 큰 테이블에서 향상 | 스냅샷 연결을 유지하는 프로그램이 필요 ([CDC 설계](./cdc.md) 4장) | 미검증 |
| B4 | 대상 VM 키우기 | CPU와 디스크 IOPS를 늘림 | 선형에 가까운 향상 | 비용 | 미검증 |

### C. 영향 범위를 줄이기

| # | 기술 | 방법 | 예상 효과 | 위험·대가 | 상태 |
|---|---|---|---|---|---|
| C1 | 읽기는 멈추지 않기 | 읽기 전용 요청은 별도 연결 풀로 보내고, PAUSE는 쓰기 풀에만 적용 | 읽기는 중단 0 | 전환 순간 짧게 오래된 데이터를 읽을 수 있음. 앱이 읽기와 쓰기 연결을 나눠야 함 | 미검증 |
| C2 | 구간별 순차 전환 | `customer_id`를 여러 구간으로 나눠 구간마다 따로 전환. 양방향 복제(`origin = none`)로 두 DB가 각자 다른 구간의 쓰기를 받음 | 한 번에 멈추는 범위가 1/N | 재고처럼 모든 고객이 함께 쓰는 행은 충돌함 → 공유 테이블은 한쪽에서만 쓰거나 누적 변화량(CRDT 카운터)으로 바꿔야 함. 시퀀스는 짝수와 홀수로 나누거나 UUIDv7. 앱 수정이 필요해 해커톤 범위 밖 | 설계만 |
| C3 | 멀티 마스터 확장 | pgEdge Spock, AWS pgactive 같은 확장으로 양쪽 동시 쓰기와 충돌 해결 | 이론상 중단 0 | 충돌 해결 규칙을 잘못 정하면 데이터가 틀어짐. 이전 도구로는 권하지 않음 | 참고만 |

### D. 체감을 줄이기

| # | 기술 | 방법 | 예상 효과 | 위험·대가 | 상태 |
|---|---|---|---|---|---|
| D1 | 요청을 기다리게 하기 | PgBouncer PAUSE로 요청을 실패시키지 않고 붙잡아 둠 | 실패 0 | 대기 요청이 `max_client_conn`을 넘으면 연결 거부 | **검증됨** (에러 0) |
